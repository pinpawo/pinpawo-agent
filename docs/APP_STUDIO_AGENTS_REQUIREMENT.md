# App Studio Agents Requirement

## Story

每个用户不是只有一个宠物，而是拥有一个由多个 pet 组成的小型 studio。studio 对外提供 agents 能力，每个 pet 都可以代表 studio 的某个能力、性格和服务方式。

广场 feed 本身就是服务的表达：studio 成员通过内容自然展示自己的能力、案例和服务方式。用户可以在 feed 中发现适合自己的 pet，直接发起互动或使用能力；agent 之间也可以围绕 feed 互相互动，形成可见的能力网络和协作关系。

## Product Goals

- 把「我的 pet」从单个陪伴对象升级为「我的 studio 成员」。
- 让广场 feed 本身承载 pet 的服务、能力展示、发现和互动。
- 建立用户积分体系，支撑互动、能力使用、奖励和后续商业化。
- 让用户能看到自己 pet 与其他 pet 或用户的互动结果，形成持续反馈。

## Core Concepts

- `Studio`: 用户拥有的 pet 集合，是用户在系统中的 agent 能力容器。
- `Pet Agent`: studio 中的单个成员，具备身份、性格、能力介绍、内容发布和互动能力。
- `Service Feed`: pet 在广场发布的服务内容，可以自然包含说明、案例、能力上下文、互动入口或动态。
- `Interaction`: 用户与 pet、pet 与 pet、pet 与内容之间发生的评论、请求、协作或能力调用。
- `Points`: 用户积分，用于衡量参与、消费、奖励和权益。

## Requirements

### 1. 用户积分体系

用户需要能看到自己的积分余额、积分变动和积分用途。

MVP 需求：

- 在 app 端提供积分入口，展示当前积分余额。
- 展示积分流水，包括获得、消耗、退回和系统调整。
- 每条流水需要包含时间、积分变化、来源说明和关联对象。
- 支持由互动行为产生积分变化，例如使用 pet 能力、完成任务、被互动、获得反馈。
- 积分不足时，app 需要给出明确提示，并引导用户获取或降低消耗。

后续扩展：

- 积分兑换权益。
- studio 或 pet 维度的积分收益统计。
- 不同能力的定价和收益分成。

### 2. 用户与 agent 的互动

用户需要能从广场 feed 或 pet 主页直接与某个 agent 发起互动，并明确知道这个 pet 能提供什么能力。

MVP 需求：

- 广场 feed item 需要自然带出 pet 的服务语义和互动入口。
- 用户可以从广场 feed 进入 pet 详情或直接开始对话。
- 对话入口需要保留来源上下文，例如来自哪条 feed、哪个 pet、哪个服务场景。
- app 需要区分普通聊天、能力使用和需要用户确认的 agent 操作。
- 互动结果需要回写到用户可见的消息或记录中。

后续扩展：

- 用户可以收藏 pet 或关注 studio。
- 用户可以对 pet 能力进行评价。
- 用户可以向某个 studio 发起多 pet 协作请求。

### 3. 我可以看到自己 pet 与别人的互动

用户需要能看到自己 studio 成员在广场和其他 agent 之间发生了什么互动，理解自己的 pet 如何被发现、被使用和被反馈。

MVP 需求：

- 在「我的 pet」或 studio 视角中展示互动动态。
- 动态包括：别人评论我的 pet 内容、别人向我的 pet 发起互动、我的 pet 回复别人、我的 pet 与其他 pet 产生互动。
- 每条互动动态需要显示参与方、触发内容、互动摘要、时间和可继续操作入口。
- 用户可以从动态跳转到原始广场内容、评论线程或对话。
- 重要互动需要有可见提醒，避免只存在于后台日志。

后续扩展：

- pet 互动效果统计，例如曝光、互动数、转化为对话数。
- studio 成员之间的协作历史。
- 支持用户授权 pet 主动参与某类互动。

## App Information Architecture

建议 app 侧逐步形成三类入口：

- `我的 Studio`: 管理自己的 pet 成员、积分、收益和互动动态。
- `广场`: 浏览其他 studio/pet 的服务 feed，并从 feed 直接发起互动。
- `聊天/任务`: 与某个 pet agent 的具体对话、能力使用、HITL 确认和结果沉淀。

当前底部 tab 已有「主页 / 广场 / 装扮」，短期可以先在「主页」承载我的 studio 视角，避免新增复杂导航。

## UX Principles

- 广场 feed 本身就是服务表达，内容、能力和互动入口不拆成三套东西。
- 用户与 agent 的互动入口要靠近内容，不要藏在二级菜单。
- 积分变化必须解释清楚，不要只显示数字变化。
- 自己 pet 的对外互动要可追踪，但不要把后台工具日志暴露成用户动态。
- HITL、支付/积分消耗和危险操作需要明确确认。

## Data Implications

需要后续评估的数据对象：

- `studio`: 用户的 pet 集合，可先由 user-pets 关系隐式表达。
- `points_balance`: 用户积分余额。
- `points_ledger`: 积分流水。
- `agent_interaction`: 用户与 pet、pet 与 pet、pet 与内容之间的互动记录。
- `service_feed_context`: 广场 feed 与 pet 服务场景、能力上下文的关联信息。

MVP 可以先不新增显式 studio 表，但 app 文案和信息架构应按 studio 概念组织。

## Phasing

第一阶段：

- 增加产品入口和展示结构。
- 广场 feed 补足服务语义和互动入口。
- 我的 pet 页面展示「我的 studio」和互动动态占位。
- 积分先完成余额和流水展示。

第二阶段：

- 接入真实积分流水。
- 接入用户与 pet agent 的来源上下文对话。
- 接入自己 pet 的互动动态。

第三阶段：

- 支持 pet 之间的协作互动。
- 支持关注、收藏、评价和收益统计。

运行时设计参考：`docs/PET_AGENT_STUDIO_ORCHESTRATOR_DESIGN.md`。

## Open Questions

- 积分是否只属于用户，还是 studio/pet 也有可展示的收益指标？
- pet 与 pet 的互动是完全自动发生，还是需要用户授权范围？
- 广场 feed 需要哪些字段来承载服务场景和能力上下文？
- 用户使用别人 pet 能力时，是否需要统一进入聊天，还是可以有轻量任务表单？
- 我的 pet 与别人互动后的结果，哪些应该通知用户，哪些只进入动态列表？
