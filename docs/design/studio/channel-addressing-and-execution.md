状态：讨论收敛稿，2026-10-05。本文固化用户已确认的产品语义，并列出建议、技术待核实项和
尚未定案的执行架构。它不是实现完成说明，也不授权发布、迁移用户配置或更新本地服务。

本文承接 [Channel 基础草案](channel-collaboration.md) 与 [Console 设计](console.md)。

## 目标与现状

围绕一件事情，人和 Pet 在同一 Channel 中明确寻址、交接和查看结果。发送以后，用户能看到
不同 Pet 的工作状态、真实排队列表，以及消息与各目标执行的关联。保留现有 Pet runtime、
Channel 会话绑定、接纳校验和权限边界，不引入 LLM check 或泛化 workflow 平台。

## 术语与已确认的消息协议

**有效 @**：已发送消息中明确寻址一个对象，并请求该对象处理。发送者可以是人或 Pet，
语义相同。正文表达要处理的工作；@ 不等于新建任务、完成任务或获得额外授权。

**收件人**：有效 @ 指定的稳定 `petId`。展示名称可变化，名称本身不能替代身份。

**引用上下文**：`replyTo` 指向的原消息。它说明本条消息在回应或引用什么，与收件人分开。

**接纳**：后端确认一次明确请求进入目标 Pet 的执行入口或队列，不等于已经开始执行。

**执行状态**：某条消息对某个目标的真实接纳与运行观察；本轮结束不表示业务目标验收完成。

用户已确认以下协议约束：

1. 草稿不生效，只有发送后的有效 @ 才构成交接。
2. 有效 @ 必须唯一解析到明确身份。目标不存在或名称有歧义时提示，不能猜测目标或默认
   交给另一个 Pet。选择器与手动 @ 采用同一身份解析规则，发送后在时间线可见。
3. 引用、代码、转述中的 @ 不作为有效目标。不是扫描所有历史正文中的 @ 就执行。
4. 同一消息对同一 Pet 去重；多个目标独立送达，不隐含串行、依赖或等待顺序。
5. 人和 Pet 使用同一有效 @ 语义。Pet 可以用有效 @ 交接，不要求另建 handoff 工具；
   有协议即可确定解析，不能把 Pet 的 @ 一概当成猜测或禁用。
6. `replyTo` 与收件人分开。引用 A 的消息不等于必须交给 A，也不授权使用 A 的 session
   执行 B 的请求。每个实际收件人仍使用其在本 Channel 的固定 session。
7. 寻址不扩大发送者已有授权范围，不绕过工具审核、人工审批或 Pet 的能力边界。

建议复用消息现有的 `mentions: [{petId}]` 作为结构化身份记录；正文和可见 @ 标识保持一致。
具体文本语法、编辑器标记与 wire schema 尚需在实施前写清。只改 UI 展示名称、不保存稳定
身份，或只用宽泛正则扫描所有正文，都不能满足上述协议。

### 笔记、请求与回复

| 消息情况 | 协议要求 | 尚需确定的接口 / UI 形式 |
|---|---|---|
| 纯笔记 | 没有有效收件人，不启动 Pet；其中引用或代码里的 @ 仍是普通内容。 | 现有 Save note 如何明确区分文字示例和有效寻址。 |
| 明确 @ 请求 | 正文加结构化目标构成处理请求，发送后按目标接纳或排队。 | 是否复用 execute、使用消息 ingress，或由规则路由；不预设全部 Trigger。 |
| 回复 | 保留引用上下文，实际收件人独立确定并可见。 | Reply 快捷动作是否默认预选原 Pet，以及如何改选；这是便利形式建议，不让 replyTo 偷换收件人。 |
| Pet @ 交接 | 同样校验有效目标、绑定与授权；交接消息和每目标结果可追溯。 | 从本轮可信公开回复提取有效 @ 的具体协议与接纳接线。 |

现有 `/channels/execute` 的 replyTo 只允许原 Pet/session，是当前实现的收窄契约。
下一阶段若支持“引用 A、寻址 B”，必须使用 B 的 Channel 绑定并明确传递引用上下文，
不能通过篡改已有 source 或放宽 session 校验达成。具体兼容入口尚未决定。

多目标的“独立送达、不隐含顺序”是已定语义；首片是否一次支持所有目标、按何顺序显示，
以及具体调度粒度尚未定案。若分期限制入口数量，必须明确提示，不能静默只送第一个目标。
本文不承诺 A 等待 B 回信、自动回传结果或多 Pet 闭环协议已经实现。

## dispatch 与 Trigger 的职责和候选选择

dispatch 是执行接纳机制；Trigger 是规则决策与路由机制，不是与 dispatch 互斥的另一个
执行器。用户已明确不能预设所有消息都必须经过 Trigger。

| 场景 | 最小候选路径 | 选择依据 |
|---|---|---|
| 用户已经明确对象与执行意图 | Channel 接纳 → `context.dispatch()` | 目标与意图已经确定，现有直接路径不是缺陷，不应仅为使用 Trigger 再加一层。 |
| 外部事件需判断是否启动、选择对象或构造请求 | 事件 → 已配置 Trigger → 对应执行接纳入口 → dispatch | 规则确实承担决策，复用既有框架。 |
| 人与 Pet 的有效 @ 共用消息寻址协议 | 候选 A：共享 Channel 消息接纳后直接派发；候选 B：消息事件由 Trigger 路由，再调用 Channel 接纳 | 需比较规则职责、事件来源、实现成本、状态可观测性与重复执行保护；尚未最终选择。 |
| 纯笔记、引用、系统状态或无效目标 | 不派发，或明确报告寻址错误 | 保存内容、展示状态与要求 Pet 处理是不同动作。 |

“有效 @ 消息统一唤醒采用 Trigger”目前是建议，不是用户已经确定的架构。UI @ 展示、
Pet 工作状态与排队列表是独立要求，不能以采用某条 Trigger 为前提。

无论采用哪个候选，都必须满足：

- 对一次 `(messageId, petId)` 请求，只有一个派发责任入口。不能 UI execute 已派发，
  相同消息事件又再派发一次。
- Channel 持有消息、目标校验、固定 session、reply 引用及 scope 的接纳所有权。
  不把事件正文或 HTTP payload 中声称的 session/scope 当成可信执行字段。
- 多目标关联不能继续用“messageId 唯一代表一场执行”的假设。每目标独立记录接纳、运行
  和失败，并关联对应 invocation/output；具体 schema 是实施项，不在本文声称已存在。
- 重复提交和重复事件须去重。一次消息对同一目标已经接纳时，重复通知不能新建一次执行。
  有歧义的断线或重启结果不能靠自动重发解决，不承诺跨进程 exactly-once。
- 若选择 Trigger，首次投递与已有 retry/redeliver 必须保留同一领域接纳校验与上下文；
  不能首次走 Channel、后续却绕回不带 session/scope 的普通 dispatch。领域接线可考察现有
  opaque Plugin hooks，但是否扩展以及具体契约仍是建议，不能提前写入平台级新架构。
- 若采用事件路径，必须区分有效交接与普通输出、引用、错误或回执。Pet 身份不是禁用 @
  的理由，系统自动回执也不能成为一次新的处理请求。

同消息去重能避免重复事件，不能证明任意 A/B 连续新增消息不会形成对话循环。多轮回信和
自动协作边界需单独定案，不以“模型自己会判断”代替协议，也不在本期附加 LLM check。

## 忙时排队、状态与 UI

### 已定要求

- 忙时收到有效 @ 可以排队，保留同 Pet 串行执行与 `(channelId, petId)` 固定 session。
- 用户明确不要发送前的 Pet 忙闲 / 排队状态提示。必要的目标身份校验不等于忙闲提示。
- 发送后必须看到不同 Pet 的工作状态与真实排队列表；这两项是必做，不只是可选回执。
- 消息时间线关联该消息每个目标的真实状态；详情展示具体目标、调用与错误。
- 队列由后端提供，前端不从消息数量、执行历史或时间差推算排队列表、次序或等待时间。
- 失败直接显示在 Channel timeline。不能自动变成 Supervisor 等用户回复，也不引入特殊
  失败重试流程、自动重试或重试按钮。

### 最小可观测状态

| 后端事实 | 发送后的展示要求 |
|---|---|
| 消息已保存，尚未确认接纳 | 已保存 / 待接纳；不能显示执行中。 |
| 目标已进入 Host 队列 | 对应 Pet 排队中，并可在真实队列列表定位该请求。 |
| Host 开始本轮 | 对应 Pet 执行中。 |
| 原生交互 / 审批等待 | 展示已有真实等待观察；原 TUI / session 处理，不新建审批恢复机制。 |
| 本轮完成或中断 | 展示本轮结束及公开结果；不把它等同目标已完成。 |
| 寻址、接纳、执行或结果保存失败 | 时间线显示与本消息 / 目标关联的具体失败；区分执行失败和执行结束后结果未保存。 |
| 断线或重启使观察不能确认 | 状态未知，保留最后已知事实；不伪装仍在执行或已经恢复。 |

没有保存成功的发送失败也必须明确为未送达，不能冒造后台 messageId 或成功记录。
准确的展示状态枚举、失败记录归属及 API 映射是实施工作；本文不新增运行状态机。
若选择事件路由，未配置规则或投递失败同样须有可见事实，不能把“消息已保存”当作“已排队”。

**位置建议，未定**：沿用现有右侧区域展示 Pet 状态和队列，时间线保留每目标简明状态；
窄屏沿用抽屉。具体位置不改变状态与列表必做的要求。

### 队列事实源与待核实边界

现有运行槽属于 resident Pet，而不是每个 Channel。一个 Pet 的不同 Channel session
以及直接 TUI 操作共享接纳边界。等待某 session 的 interrupt 时，其他符合条件的 session
可能绕行，因此不能把现有队列描述成各 Channel 独立的严格 FIFO。

需先核实并补充最小只读队列投影：当前活动操作、尚未执行条目的稳定身份、实际 Pet、
可公开的 Channel / 请求关联和后端当前队列信息。全局忙的原因与当前 Channel 的请求列表
须可区分；其他 session 的私有内容不能因展示队列而进入公共 Channel。

投影如何划分 Pet 全局状态与 Channel 局部条目、由哪个现有 API 承载、条目顺序如何表达，
是技术待核实项。添加投影不等于增加持久队列，不承诺离线恢复或预计完成时间。

## 排队回执与反馈边界

Pet 自己回复“已排队”是可选行为，不是状态展示的必要条件，不要求额外模型调用。

建议由系统渲染带 Pet 身份的自动回执，明确标注系统来源，零模型调用；回执不含有效 @
请求、不进入交接路由，重复回执可合并避免刷屏。此实现形式尚未由用户确认。
可以先只显示真实状态与队列，不能因此省略用户已要求的这两项 UI。

错误、队列回执和生命周期更新本身不触发新的 @ 请求。失败交由用户按上下文判断，
不自动新建任务、不自动重发、不把技术失败包装成 Supervisor 的自然追问。
真实业务追问仍是普通 Pet 回复；等待 A/B 回信的协作协议尚未确定。

## 已定、未定与非本期承诺

| 分类 | 内容 |
|---|---|

## 最小分阶段实施建议

1. **协议与接纳边界**：明确有效 @ 的表示、身份校验、引用排除、重复目标处理与发送动作；
   核实队列事实源，比较直接接纳与 Trigger 路由。先定单一派发责任，不边实现边默认架构。
2. **寻址与真实观察**：复用现有消息 / 执行接口和 Pet registry，让选择器、手动 @ 与
   时间线一致；补充后端只读 Pet / 队列投影，发送后显示状态和列表。保留 fixed session
   与权限约束，不加入取消、插队或发送前状态提示。
3. **交接与选定路径**：按定案接入人和 Pet 的有效 @，支持目标间独立送达、可追溯结果与
   timeline 失败。若选择 Trigger，仅补齐必要领域接线与重复投递保护；若选择直接接纳，
   不为展示状态强加 Trigger。旧消息 / 历史输出不得因为升级而自动重新执行。
4. **验收与可选回执**：运行下列行为验收；自动排队回执只有在形式确认后加入，否则保留
   已要求的状态与队列。明确实际覆盖，不以确定性测试声称真实模型协作已验证。

这些是建议实施顺序，不意味着全部阶段已经批准开发或发布。此次文档提交不含实现。

## 验收清单

| 用例 | 应观察到的结果 |
|---|---|
| human @ | 选择器和手动有效 @ 解析到同一 petId；发送后 timeline 显示该目标，正文工作准确交接，一目标一次接纳。 |
| 目标异常 / 草稿 | 未发送草稿不执行；不存在或歧义目标明确提示；不转交默认 Pet。 |
| 引用与代码 | 代码、引用和转述中的 @ 不唤醒 Pet；纯笔记不执行。 |
| Pet @ handoff | 可信公开回复中的有效 @ 可交接到对应 Pet，身份和来源可追溯；不要求额外 handoff 工具，不扩大权限。 |
| 多目标与重复目标 | 同消息同 Pet 一次；各目标状态独立，某目标失败不把其他目标变成失败，不制造未约定依赖。入口暂有限制时明确提示。 |
| busy queue | 在同 Pet 已忙时发送：不增加发送前状态提示；发送后后端队列出现真实条目，空闲后按实际接纳规则运行，不与该 Pet 当前执行重叠。 |
| 全局与局部 | 同 Pet 跨 Channel / TUI 工作时，全局忙与本 Channel 请求可区分，固定 pair session 不串线，不暴露私有 session 内容。 |
| 重复提交 / 重复事件 | 同一请求对同一目标不重复执行；公开结果不重复入库。UI 派发与事件消费者不能各执行一次。 |
| reply binding | 同 Pet 回复复用其 Channel session；引用上下文与显式收件人分别展示和校验。若交给 B，使用 B 的绑定，不能借 A 的引用取得 A 的会话或权限。 |
| 失败 timeline | 接纳失败、执行失败和结果保存失败准确呈现；不自动转成等回复、不自动重试、不出现新增失败重试按钮。 |
