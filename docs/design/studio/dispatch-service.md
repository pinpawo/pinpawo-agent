# Resident Dispatch controls

The Host exposes controls on `resident.dispatch`. Studio's existing submission port and Pet Head are unchanged. The resident coordinator remains the only owner of the work queue and execution slot.

- `dispatch(request)` accepts ordinary work under the existing admission rules.
- `stop(target)` requests cancellation of the exact active selection from the queue snapshot. The caller passes only its dispatch ID. The coordinator rejects ID reuse for the lifetime of the resident, even after settlement or supersession. Studio already assigns a fresh UUID and handles retries with its own idempotency key. Dispatch controls do not carry across a resident restart. A selected but unstarted entry does not open an Agent request. An executing entry uses the existing request cancellation. A positive acknowledgement is not completion. The coordinator fences that resident’s queue before signalling cancellation, then retains the slot through Agent settlement and the settled-state read. Writers wait on that barrier without becoming queued work or publishing a lifecycle event. After release, admission uses the live queue as usual. A cancelled or timed-out writer never enters the queue. Observations stay available. If the stopped turn’s checkpoint cannot be read, the queue stays fenced and refresh retries that same checkpoint. A failure to save Dispatch attribution after a confirmed graph outcome reports failure without retrying the graph read. A replacement on the same thread cannot enter before cancellation settlement completes. If writers are already waiting when confirmation fails, they share one automatic retry without resetting their deadlines. The selected TUI Session cannot confirm settlement on its behalf. A native review discovered on that retry stays bound to the stopped dispatch. An execution resumed through the Session's review entry point is controlled through the existing Session path, not this queue control.
- `supersede(request, options)` requires an existing, explicitly addressed Session and scope; it does not create a Session. It validates every named pending ID against the live queue, removes those pending entries from scheduling, emits an observable `superseded` lifecycle, and admits the replacement at the tail. If any ID is stale, ambiguous or out of scope, neither queue change is applied. Other entries retain their ordering; this is not a priority change. If supplied, an exact stop target in the same Session and scope is handled separately after admission; its receipt (`requested`, `not_active`, or `not_requested`) does not change whether replacement work was admitted.

An asynchronous readiness check is not a reservation of its candidate. The coordinator rechecks live membership before claiming it, so a superseded candidate cannot execute when its old readiness check finally completes. Ready-item FIFO, not global strict FIFO, still applies. The queue and its lifecycle events do not become durable storage through this change.

### Review answers

Studio and TUI submit Review answers through the same resident coordinator entry point. An answer reserves the Pet execution gate from admission through settlement, but never enters the Dispatch FIFO. A concurrent answer is refused, not queued. Session and model listings are observations; they do not hold the execution gate or write the Session registry. The Session still checks the target interrupt and uses its existing checkpoint to resume the same run. The coordinator does not decide how to answer, and queue Stop behavior is unchanged. The Host resolves the Session once, then uses that Session to read, validate, and resume the current interrupt through LangGraph, not from the client Session snapshot. The ordinary TUI targets its active Session; the Studio endpoint targets the Session named in the request and does not change TUI selection. The HTTP receipt says the targeted interrupt was current; the Session stream reports whether the answer was valid and applied. The Host execution layer settles the run. A waiting result carries the current interrupt explicitly, and Dispatch records that result without reconstructing it from events or rereading the graph. Session events notify observers; they are not an input to settlement.

An answer to an interrupt left by a dispatched turn gets its own Dispatch ID and references the dispatch that left that interrupt. If resume fails and the same interrupt is still pending, the answer dispatch reports failure without taking ownership of the original interrupt. A successful continuation that suspends on a new interrupt leaves a new waiting Dispatch. A Session status is only as current as the Session read; the answer's outcome does not substitute for it.
