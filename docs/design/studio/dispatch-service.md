# Resident Dispatch controls

The Host exposes controls on `resident.dispatch`. Studio's existing submission port and Pet Head are unchanged. The resident coordinator remains the only owner of the work queue and execution slot.

- `dispatch(request)` accepts ordinary work under the existing admission rules.
- `stop(target)` requests cancellation of the exact active selection from the queue snapshot. The caller passes only its dispatch ID. The coordinator rejects ID reuse for the lifetime of the resident, even after settlement or supersession. Studio already assigns a fresh UUID and handles retries with its own idempotency key. Dispatch controls do not carry across a resident restart. A selected but unstarted entry does not open an Agent request. An executing entry uses the existing request cancellation. A positive acknowledgement is not completion. The coordinator fences that resident’s queue before signalling cancellation, then retains the slot through Agent settlement and the settled-state read. Writers wait on that barrier without becoming queued work or publishing a lifecycle event. After release, admission uses the live queue as usual. A cancelled or timed-out writer never enters the queue. Observations stay available. If the stopped turn’s checkpoint cannot be read, the queue stays fenced and a subsequent refresh retries that same checkpoint. The selected TUI Session cannot confirm settlement on its behalf. A native review discovered on that retry stays bound to the stopped dispatch. An execution resumed through the Session's review entry point is controlled through the existing Session path, not this queue control.
- `supersede(request, options)` requires an existing, explicitly addressed Session and scope; it does not create a Session. It validates every named pending ID against the live queue, removes those pending entries from scheduling, emits an observable `superseded` lifecycle, and admits the replacement at the tail. If any ID is stale, ambiguous or out of scope, neither queue change is applied. Other entries retain their ordering; this is not a priority change. If supplied, an exact stop target in the same Session and scope is handled separately after admission; its receipt (`requested`, `not_active`, or `not_requested`) does not change whether replacement work was admitted.

An asynchronous readiness check is not a reservation of its candidate. The coordinator rechecks live membership before claiming it, so a superseded candidate cannot execute when its old readiness check finally completes. Ready-item FIFO, not global strict FIFO, still applies. The queue and its lifecycle events do not become durable storage through this change.
