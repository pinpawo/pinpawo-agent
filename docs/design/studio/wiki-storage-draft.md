# Studio 项目知识目录（工作草案）

状态：草案；本次实现和验证后仍需审查。知识是有价值的持久数据，不是运行缓存。

## 目标与边界

Studio 使用一份可浏览、可由被授权的 Pet 维护的 Markdown 知识，不把生成的 Wiki 写入业务代码仓库。多个 Channel 使用同一 Studio 时共享这份知识；代码仓库和各 worktree 可作为知识来源，不决定知识的存储目录。不同 Studio 和不同机器的内容不会因此自动合并或同步。这里不引入多项目注册、远程同步或知识版本管理。

## 目录和身份

新初始化的 Studio 在用户数据目录下创建独立的、随机标识的持久目录，例如 `~/.pinpawo/studios/<uuid>/wiki/`，并把绝对路径持久写入 Project Files Plugin 配置的 `wikiDirectory`。标识不依赖仓库名称、worktree 路径或默认 `studioId`。原有 Studio 配置不自动改写；迁移由用户明确发起，目标已存在内容时不得覆盖。初始化和迁移均需保留已有文件，失败不能删除已有用户数据。

`wikiDirectory` 是受信任的本地启动配置，不是 HTTP 请求参数。Project Files 使用该根提供 Knowledge 只读接口和有边界的 Pet 文件操作；API / 工具只接收根内的规范化相对 Markdown 路径，不允许通过绝对路径、`..` 或软链接越界。历史 `directory` 相对 workdir 的配置仍按旧边界读取，避免静默搬迁已有知识。新旧选项不可同时设置。

## 读写与协作

Console Knowledge 和 Channel 的入口都展示同一目录。Wiki 并非 Channel 成员或 Agent Session 的新类型；Pet 使用 Plugin 提供的通用项目文件能力，源代码工具和工作目录不因此取得更宽的授权。工具写入沿用现有操作审核策略，不能把 Channel 成员身份当作文件读取授权。初版面向本地 Studio 身份；其他客户和跨机器访问仍需明确授权和同步设计。

Wiki 更新先读现状、保留人工修改并检查引用；变更不依赖业务仓库 Git。需要把知识转为业务仓库文档时，应由明确授权的项目工作完成。知识目录需纳入用户的备份与恢复，不能随普通会话或缓存清理而删除。

## 迁移与未决事项

迁移时先复制现有内容，核对文件清单与字节，更新 Studio 指向并验证页面和 Pet 读取；确认之后才把旧副本移到可恢复备份，不得直接删除已有文件。中途失败保留源数据并回退配置。多 Studio 显式共享知识、并发写入和远程备份策略留待独立设计，不能凭 repo 名或 URL 自动合并。

## 并发写入与锁恢复

`project_files_write` 要求先读取并携带内容摘要；合作的 Toolkit 写入按页面锁串行，新页面另经根级创建锁和数量检查。它在替换前再次检查内容并使用原子文件替换；未配置目标、摘要不匹配或锁已存在时拒绝写入。锁包含创建进程 PID 与时间，不按时间自动删除；出现残留锁时，先人工确认对应进程已停止，再手动移除报错所指的锁文件。

这些锁只协调遵守相同协议的写入方。普通编辑器、Shell 或其他不遵守锁的进程，仍可能在最终比较与替换之间竞争；当前 Node 的路径式文件操作也无法完全排除有权限的本机进程在校验与写入之间恶意替换目录或软链。请避免并行操作同一知识目录；需要更强的多进程/对抗性保证须另设计，不能把当前检查说成全局原子 CAS。
