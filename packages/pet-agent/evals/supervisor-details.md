# Supervisor Capability 详情披露 eval

运行 `npm run eval:supervisor-details -w @pinpawo/pet-agent`。使用本地模型 Profile 和服务端默认参数，不执行 Capability 业务工具，也不上传 tracing。

可选环境变量：

- `PROMPT_EVAL_PROFILE_ID`：选择模型，与其他 decision eval 相同。
- `DETAILS_EVAL_REPEATS`：每个场景重复次数，默认 1；观察稳定性建议多轮。
- `EVAL_CASES`：逗号分隔的场景名；未知名称报错。
- `DETAILS_EVAL_REPORT_PATH`：完整 JSON 报告路径，默认系统临时目录。

| 场景 | 阶段 | 最大详情调用数 | 行为要求 |
|---|---|---:|---|
| entry-exact-capability | Entry | 0 | manifest 支持直接提交计划 |
| entry-disclosed-capability | Entry | 0 | 已披露文档足够，直接提交计划 |
| entry-two-responsibilities | Entry | 0 | manifest 支持提交完整计划 |
| entry-requested-details | Entry | 1（必须调用） | 用户要求先读完整详情，然后安排计划 |
| entry-user-choice-before-work | Entry | 0 | 用户要求先询问，不先探索 |
| boundary-accept-no-discovery | Boundary | 0 | 已有证据足够，验收并回复 |
| boundary-continue-no-discovery | Boundary | 0 | 测试未执行，将缺口交回当前 delegation |

这些是受控 fixture 的效率预期，不是通用运行时限制。注册表含 5 个职责互异的 Capability，包括干扰候选。每例使用新 runner，首次路由清单生成计入模型调用与耗时，避免只呈现缓存命中的结果。

两个 Boundary fixture 使用同一个明确任务：修复购物车小计忽略单价的问题，为指定输入增加回归测试，并运行目标测试及全量测试。成功结果提供根因、文件改动、修复前失败和修复后两次测试的命令、退出码及统计；未完成结果保留相同改动，但明确修复后尚未运行测试。它们是合成的执行报告，不是本仓库实际执行记录。预期仍分别为验收并回复、继续当前 delegation，不通过模糊的“已完成”声明或直接告诉模型应该选哪个控制动作来取得通过。

报告复用现有诊断收集器，包含详情调用次数、含详情调用的模型轮数、请求名称、返回的披露信息，并包含：

- 每次模型/工具调用的开始时间、持续时间、完成/失败/仍等待状态。
- 模型提出的工具名称，帮助区分提出调用和实际执行。
- 相同 names（忽略大小写和顺序）的重复请求次数。
- 模型调用总数、整体耗时，以及独立的行为/披露预算判定。

并行两次详情调用 计为两次调用、一轮。工具结果按回调完成顺序记录；详细时序按 run id 关联工具的开始/结束事件。实际执行次数超过预算或相同名称请求重复都判失败。超时/异常仍输出已收集的调用轨迹；没有返回的调用保留 pending，不能把它的耗时误记为零。

局限：这是 Supervisor 专项，不运行 root 全图；现有完整生命周期 eval 继续负责节点交接和 checkpoint 验收。详情结果区分已经披露和未知名称；重复请求判定不做额外模型判断。一次通过不代表长期稳定率。

DeepSeek V4 Pro 与 Qwen3.8 Max 使用服务端默认参数，各跑一轮，均 5/6 通过。两者搜索次数一致：

| 场景 | DeepSeek | Qwen |
|---|---:|---:|
| 明确单 Capability | 1 | 1 |
| 文档已披露 | 1（预期 0，失败） | 1（预期 0，失败） |
| 两种职责 | 2，同一轮 | 2，同一轮 |
| 先询问用户 | 0 | 0 |
| Boundary 验收 | 0 | 0 |
| Boundary 继续 | 0 | 0 |

失败均为再次搜索已披露的 repository，返回无新增文档，最终控制动作仍正确。本轮没有观察到多轮搜索失控；保留该失败作为效率回归目标，不调整阈值迁就结果。时序同时表明首次路由清单生成也是模型调用，不能把其耗时误归为 capability_search。


## 当前契约调整

上述首轮结果是旧 capability_search 的历史基线。新工具为 capability_details(names)，精确名称读取，无关键词搜索。明确职责的 manifest 场景预期直接安排；增加 entry-requested-details，用户明确要求先读完整详情时必须调用一次并正确提交计划，防止通过“永远不读详情”取得低调用数。新一轮结果分别报告，不能把前后工具次数不加解释地等同。

运行时已移除空披露轮数、open/closed 和模型/工具调用轮次记录，只合并已披露名称。eval 中的调用次数、轮数和耗时继续保留，它们只用于观察与验收，不会关闭详情工具。运行时继续保障读取配额；Supervisor 已移除总时间限制，保留调用方主动中断。下方 60 秒超时记录属于移除前的历史实验。

## 改为详情披露后的实测（同日，各一轮）

- DeepSeek V4 Pro：6/7；5 个 Entry 场景全部通过。明确单能力、已披露文档、两种职责和先询问场景均 0 次详情调用；明确要求先读详情时调用 1 次。Boundary 验收场景未调用详情工具，但总时限 60 秒到期（路由清单约 15 秒，之后模型仍等待）；另一个 Boundary 通过。
- Qwen3.8 Max：6/7；两种职责场景批量读了两个能力的详情（1 次调用），计划正确，但未达到本 fixture 的 0 次效率目标；其余场景通过，明确要求读取时调用 1 次。
- 原有 supervisor-boundary 8 场景使用 DeepSeek Pro 重跑：8/8，包含自然询问后的用户补充续接。
- 全仓单测：1700 通过、5 跳过、0 失败；pet-agent 类型检查及 context audit 通过。

旧搜索与新披露共用场景中，“已披露仍重复获取”由两个模型各 1 次变为各 0 次。模型/网络耗时与详情调用次数分别观察，不用降低判断标准或增加强制工具限制取得通过。

## 移除私有计数状态后的复测

DeepSeek V4 Pro 默认参数单轮 6/7，所有 Entry 场景通过；仅 Boundary 验收在 60 秒总时限停止，详情调用为 0（路由清单约 22 秒，后续模型等待至超时）。全仓单测 1693 通过、5 跳过、0 失败；pet-agent 类型检查和 context audit 通过。删除已失效的计数/关闭测试，新增四次空披露后仍可读新详情、并行名称合并不丢失、已知文档不重读的行为测试。

## Boundary example 具体化后的复测

旧成功 fixture 仅声明修复完成、42 项测试通过。诊断重跑 5 次时，模型 2 次接受、3 次以缺少具体改动及测试证据为由拒绝，工具调用均正常。补充上述明确任务和执行报告后，使用 DeepSeek V4 Pro 默认参数，对两个 Boundary 场景各跑 3 次：6/6 通过。成功场景均 completed=true 并回复，未完成场景均 completed=false。

这次只修改 fixture，保留每例新 runner、60 秒总时限及模型默认 thinking。Boundary 模型耗时 4.1–9.0 秒，含清单初始化的总耗时 16.7–27.5 秒；每次仅一次 review_current，详情调用均为 0。eval 类型检查通过。结果支持具体上下文改善本组验收稳定性，但样本有限，不能据此认定此前超时的唯一原因或保证其他模型同样稳定。

## 简化路由与文档读取后的复测（2026-09-08）

Supervisor 已移除自身总时限；本次评测仍使用评测客户端既有的 120 秒单请求网络超时，它不是 Supervisor 运行时限制。这是单轮合成用例结果，不代表长期稳定率。
